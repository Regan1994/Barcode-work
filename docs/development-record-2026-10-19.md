## 1. 文件目的

本文件記錄 INTJR 條碼報工系統從初始版本到目前版本的開發過程、需求決策、資料結構演進、已完成工作、測試結果與後續待辦，作為日後回家繼續開發、交接與追蹤需求的基準。

本系統是 Windows 本機離線使用的 Flask + SQLite 應用程式，主要用於：

- 建立產品製號與報工批次。
- 列印及重新列印 60×60 mm START／FINISH 標籤。
- 使用 USB HID 條碼掃描器更新報工狀態。
- 查詢報表、匯出 Excel，以及留下掃描與操作稽核紀錄。
- 支援標準四軸與五軸產品的不同組裝階段。

## 2. 開發起點與總體方向

最初版本已具備 Flask、SQLite、機型／機台主檔、報工、條碼掃描、標籤列印、報表與測試骨架。後續開發的主要方向，是將原本偏向「機台報工」的流程，調整成現場真正需要的「產品製號批次報工」：

1. 新產品以產品製號識別，不再要求現場先維護大量機台主檔。
2. 批次建立時直接依年份、起始流水號及台數產生連續製號。
3. 同一批產品共用 START／FINISH 條碼，但報表仍保留逐台明細。
4. 以組裝人員、組裝階段及產品製號保存實際生產資訊。
5. 保留舊資料欄位與歷史 snapshot，避免既有資料失去相容性。

## 4. 重要業務決策

### 4.1 產品製號

- 一個製號代表一個產品。
- 製號格式為「製號字首 + 年號 + 流水號」，例如 `E27-01`。
- 年號為製作年份加 1 的末兩位；2026 年製作使用 `27`。
- 批次建立時由操作人員輸入製作年份、起始流水號與台數，系統依序產生製號。
- 已使用的製號不可重複建立。
- 已確認的機型字首：`HR-255＝E`、`AR-210＝C`、`AR-170＝B`、`RC-210＝CR`、`RC-255＝ER`。

### 4.2 批次報工

- 同一批產品各自保存一筆報工明細。
- 同批產品共用一張 START 與一張 FINISH 條碼。
- 掃描 START 後，整批產品同步進入進行中。
- 全批產品完成後掃描 FINISH，整批同步完成。
- FINISH 不另外輸入完成數量，批次台數就是本批產品數量。

### 4.3 舊機台資料

- 新產品報工不再需要先建立或選擇機台主檔。
- 舊機台主檔、舊機台編號、歷史 snapshot 與舊欄位仍保留，供歷史資料相容。
- 系統設定中的「舊機台編號語意」已移除，因為新流程不使用這項功能。
- 不將舊機台編號，例如 `E-01`，重新解讀成新的產品製號。

### 4.4 組裝人員

- 新報工從啟用中的組裝人員清單選取人員，不再自由輸入姓名。
- 組裝人員可以新增、停用及重新啟用。
- 停用人員不會影響歷史報工；報表篩選仍包含停用及歷史人員。

## 5. 五軸多階段組裝

使用者確認「旋傾尾」實際上是三台四軸的組合，因此五軸產品需要拆成四個組裝階段：

| 顯示名稱 | 代碼 | 意義 |
|---|---|---|
| 旋轉軸 | `旋` | 旋轉軸組裝 |
| 傾斜軸 | `傾` | 傾斜軸組裝 |
| 尾座 | `尾` | 尾座組裝 |
| 組合 | `組` | 將旋、傾、尾組合成完整產品 |

規則如下：

- 機型名稱以 `F` 開頭時，建立批次必須選擇上述一個組裝階段。
- 標準四軸機型不使用組裝階段，下拉選單 disabled。
- 五軸產品製號以 `SS` 開頭，例如 `SS27-01`。
- 同一個製號可以建立不同階段，例如 `SS27-01／旋` 與 `SS27-01／傾`。
- 同一製號同一階段不可重複建立。
- 階段會保存於批次、產品報工、重新列印資訊及條碼內容。
- 掃描時會驗證階段，避免把旋轉軸條碼掃到傾斜軸流程。
- 只有同一製號的旋、傾、尾都完成後，才具備進入組合階段的條件。
- 產品只有在組合階段完成後，才視為整台產品完成。

例如 `SS27-01` 的旋、傾已完成，但尾座尚未完成時，不能將 `SS27-01` 視為可組合；不同製號的階段不能互相替代。

## 6. 已完成的主要功能

### 6.1 機型與資料主檔

- 機型主檔主要輸入機型名稱與製號字首。
- 新機型的內部代碼由機型名稱自動建立；既有機型的舊代碼保留。
- 可停用或刪除機型；有報工或舊機台關聯時禁止直接刪除。
- 刪除前會建立並驗證 SQLite 備份，並留下稽核紀錄。
- 機型頁面的保存與刪除按鈕已調整為同一列，不再換行。

### 6.2 最近批次與刪除

- 最近批次頁列出最近 20 批。
- 可以重新列印原批次標籤，沿用原製號、批次與條碼。
- 可以刪除誤鍵或取消的批次。
- 刪除具備 CSRF、防止誤刪的二次確認、批次識別確認與刪除前備份。
- 刪除範圍包含批次、產品明細、條碼及相關掃描紀錄；刪除稽核紀錄保留。

### 6.3 掃描與導覽

- 主頁提供直接掃描報工。
- 主頁右上角新增「報工掃描」快捷連結。
- 「報工掃描」使用獨立頁面，不要求輸入操作者，掃描後直接顯示結果。
- 掃描結果顯示處理內容、時間與實際掃描到的資料。
- 使用者介面名稱統一為「報工掃描」。

### 6.4 時間與報表

- 資料庫仍使用 UTC 儲存時間。
- 畫面、報表、列印與 Excel 統一顯示台灣時間。
- 顯示格式固定為 `YYYY-MM-DD HH:mm:ss`，例如 `2026-10-19 11:15:20`。
- 報表支援日期、機型、製號、狀態與組裝人員篩選。
- Excel 匯出為單一明細工作表，包含機型、製號、狀態、開始時間、結束時間、時長及組裝人員。

### 6.5 標籤與條碼

- 標籤尺寸以 60×60 mm 為目標。
- 標籤包含機型、台數、製號範圍、組裝人員及組裝階段資訊。
- START 位於上方，FINISH 位於下方。
- 五軸條碼加入階段識別。
- 條碼內容維持短格式，批次完整資料由 SQLite 保存。
- 重新列印沿用原始條碼，不重新產生新的批次或製號。

## 7. 資料庫與 migration 演進

系統以 `schema_migrations` 管理 schema 版本，沒有使用 SQLite `PRAGMA user_version` 作為版本管理。

| Migration | 內容 |
|---|---|
| v3 | 允許新產品報工不綁定舊機台，加入產品製號、製作年份與製號唯一性。 |
| v4 | 新增組裝人員主檔。 |
| v5 | 允許新產品報工不填寫舊機台 snapshot，既有歷史 snapshot 保留。 |
| v6 | 新增 `production_batch.assembly_stage`，保存五軸組裝階段。 |
| v7 | 新增 `job_run.assembly_stage`，回填既有五軸資料，將唯一性改為「產品製號＋組裝階段」。 |

資料保護原則：

- 不刪除既有歷史欄位。
- 不改寫舊機台與歷史 snapshot 的意義。
- 破壞性刪除前先建立並驗證資料庫備份。
- `instance/intjr.db` 與 `instance/backups/` 不加入 Git 提交。

## 9. 尚待現場確認的事項

目前程式與自動化測試已完成，但以下項目仍需實際設備驗證：

1. 以實際 60×60 mm 熱印機確認標籤邊界、字體、長機型第一行排列與實際列印位置。
2. 以現場 USB HID 條碼掃描器確認 START／FINISH 及四種組裝階段條碼都能正確讀取。
3. 確認整批 START 後狀態同步、全批完成後 FINISH 的現場操作流程。
4. 確認部分製號完成時，「組」階段要列出可組合清單，或必須等待整批完成。
5. 確認報表要以產品最終狀態為主，或同時顯示旋、傾、尾、組的階段明細。
